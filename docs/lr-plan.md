# Logistic Regression を用いた点字変換エンジンの再設計

## 1. CRF実装からの教訓と移行の背景

CRFを用いた実装を進める中で、以下の3つの重大な実装課題が明らかになりました。

### ① 学習時間の爆発的増加

CRFは系列全体の最適解を求めるため、訓練段階で複雑な計算（対数尤度の最大化、Viterbiアルゴリズムの繰り返し実行）が必要です。

* **実測値：** わずか1000行程度の訓練データで、学習に数時間以上を要する（CPUの小規模環境ではさらに深刻）
* **スケーラビリティの問題：** データが増えるほど二次関数的に計算量が増加し、実用的な訓練サイクルが困難

### ② 推論時間の遅延

* **予測の計算コスト：** 1文あたりの処理時間がSudachiなどの従来の辞書ベース手法より**大幅に長い**
* **スループットへの影響：** リアルタイムな点訳、特に点字ディスプレイへのストリーミング出力が遅延するリスク

### ③ メモリ消費の肥大化

CRFモデルは、全ての特徴の組み合わせに対する重みを保持します。

* **実測値：** 1000行程度のデータでも30MB以上のモデルサイズ（訓練過程でさらに多くのメモリを消費）
* **組み込みデバイスの制約：** 32MB以下のメモリを想定していた元の設計指針と乖離

### 結論：CRFは「強力だが重い」

CRFは強力な手法ですが、点訳という**軽量高速が求められるユースケース**では、オーバースペックであることが判明しました。

---

## 2. 解決策：Logistic Regression への転換

**Logistic Regression（ロジスティック回帰）**は、CRFよりもはるかにシンプルな線形分類器です。

### 2.1 Logistic Regression の基本概念

#### 特徴概要

* **単一の線形モデル：** 各特徴（文字、文字種、前後の文字）に対して線形の重みを学習するだけ
* **文字ごとの独立判定：** 系列全体の最適化ではなく、各位置で「このラベルが来る確率」を局所的に計算（計算量が圧倒的に少ない）
* **統計的な確率解釈：** 出力は各ラベルの確率分布となり、条件付き確率の理解が直感的

#### 数学的な定義（簡略版）

入力特徴ベクトル $X = (x_1, x_2, ..., x_m)$ が与えられたとき、ラベル $Y$ の条件付き確率は以下のように定義されます：

$$
P(Y=1|X) = \frac{1}{1 + \exp(-w \cdot X - b)}
$$

ここで：
- $w$ は各特徴に対する線形の重み（学習パラメータ）
- $b$ はバイアス項
- 計算は単純な行列演算のみで、複雑な最適化アルゴリズムが不要

つまり、**「この特徴の組み合わせなら、確率的にこのラベル」という線形関係を学習**し、未知の入力に対して高速に推論します。

**多クラス分類への拡張（点訳での使用）**

点訳では読みラベルが数百～数千個になるため、多クラス対応が必須です。scikit-learn では以下の戦略で対応します：

* **One-vs-Rest (OvR)** ：各クラス $c$ に対して、「クラス $c$ か否か」の2値分類器を訓練。
* **Decision Function** ：新しい入力に対して、全クラスのスコア $s_c$ を計算します：

$$
s_c(X) = w_c \cdot X + b_c
$$

例えば1000個のラベルがあれば、1000次元のスコアベクトルが得られます。

* **確信度への変換（Sigmoid）** ：最大スコアのクラスを選んだ後、そのスコアを sigmoid で正規化して「信度（0～1）」に変換：

$$
\text{confidence} = \frac{1}{1 + \exp(-s_{\text{selected}})}
$$

これにより、低い信度のラベルに対しては後述のフォールバックルールを適用できます。

### 2.2 Logistic Regressionの実用例

Logistic Regressionは以下のような「分類タスク」で最も効果的です：

1. **テキスト分類（スパムメール検出、感情分析）**
   - シンプルな特徴量で高い精度
   - リアルタイムな推論が必要な場合に最適

2. **医療診断の補助**
   - 複数の測定値から疾患の確率を推定

3. **CTR予測（クリック率予測）**
   - 広告プラットフォームで、ユーザーの行動確率を初期判定

4. **推薦システムの基礎モデル**
   - 単純だが高速で、複数の候補をスコアリング

5. **系列ラベリングの簡易版**
   - 各位置の判定が独立に近い場合

6. **多クラス分類（scikit-learnの LinearSVC/Logistic Regression）**
   - 数百～数千のクラスを効率的に処理
   - 点字では「読みラベルの多様性」（1000+の異なる読み）への対応に用いられる
   - decision_function でプロトタイプのスコアを取得し、確信度を計算

### 2.3 点訳への Logistic Regression の応用メリット

#### ① 圧倒的な学習速度の高速化

CRFの場合：数時間
→ **Logistic Regression：数秒〜数分**

| 項目 | CRF | LR |
|------|-----|-----|
| **学習アルゴリズム** | 確率的勾配法 + Viterbi検索 | 確率的勾配法のみ |
| **学習時間（1000行）** | 1～5時間 | 数秒～30秒 |
| **反復計算** | 複雑な系列最適化 | シンプルな重み更新 |
| **実用性** | 重い前処理が必要 | データ取得後すぐ実行可能 |

**メリット：** データのフィードバックループが爆速になり、「誤変換を記録 → 即座に再学習 → 修正版を配布」という反復改善が実現可能

#### ② 推論速度の大幅改善

* CRF: 複雑な動的計画法
  * 1文あたり 50～200ms

* Logistic Regression: 線形変換のみ
  * 1文あたり 5～20ms（辞書ベースと同等か更に高速化可能）

**メリット：** オンラインでのリアルタイム推論が容易になり、点字ディスプレイへの遅延出力が実現可能

#### ③ メモリ効率の革命的改善

| モデル | 訓練時メモリ | モデルサイズ | 推論時メモリ |
|--------|------------|-----------|-----------|
| **CRF** | 500MB～数GB | 30MB～100MB | 100MB～ |
| **LR** | 50～100MB | 1～5MB | 10～30MB |

**メリット：** 32MB制約の組み込みデバイスで、実装的な余裕が生まれる

#### ④ 実装の単純化と版のパイプライン構築

Logistic Regressionは多くの標準ライブラリに実装されており（scikit-learn, TensorFlow, PyTorchなど）：

```python
# サイコーシンプル
from sklearn.linear_model import LogisticRegression

model = LogisticRegression(max_iter=1000)
model.fit(X_train, y_train)          # 学習
predictions = model.predict(X_test)  # 推論
```

点訳では、読み推論と分かち書き判定を**独立した2つのモデル**で実装：

```python
# 读み推论モデル（多クラス： LinearSVC）
model_read = LinearSVC(max_iter=2000)
model_read.fit(X_train, y_read)

# 分かち書き推論モデル（2値: SGDClassifier）
model_boundary = SGDClassifier(loss='modified_huber')
model_boundary.fit(X_train, y_boundary)
```

**メリット：** CRFの複雑な特徴設計、ハイパーパラメータチューニングが不要で、独立したモデルの組み合わせで柔軟性を確保

#### ⑤ モデル圧縮がさらに効率的

* **線形モデル** → 重みベクトルのみで記述可能（数KB～数百KB程度）
* **バイナリ化・固定小数点化** が容易
* **モデルの可視化・解釈** が簡単（どの特徴が重要かが一目瞭然）

## 3. Logistic Regression の限界と克服方法 — 多段階フォールバック戦略

Logistic Regressionは圧倒的に高速・軽量ですが、CRFと異なり**各位置の判定が独立**であるという設計上の制約があります。この限界を補うため、本実装では**多段階のフォールバック戦略**を採用しています。

### 3.1 系列レベルの依存性が考慮されない

**制約：**
* CRF の場合：「前の文字が**何であるか**」が数学的に反映される
* LR の場合：「前の文字が**何か**」は特徴として入力するが、**モデル自体が系列の整合性を保証しない**

**例：** 
- 「東京都」という3文字を LR で推論すると、各文字が独立に読みを確定します。
- CRF なら「この3文字の組み合わせで最も自然な読み系列」を探索しますが、LR はそこまでしません。

### 3.2 多段階フォールバック戦略

本実装では、LRの独立性の制約を、**複数層のフォールバックルール**で補完しています。推論パイプラインは以下のような決定フローを持ちます。

#### 🌟 フォールバック戦略の全体構造

```
入力テキスト
    ↓
[前処理] ASCIIバイパス検出 + カスタム辞書マッチング
    ↓
[推論] LinearSVC（読み） + SGDClassifier（分かち書き）
    ↓
[後処理] 多段階の決定根拠タグで精緻化
    ├─ BYPASS：ASCII文字（バイパス済み）
    ├─ DICT：カスタム辞書でマッチ
    ├─ LR：LRの予測を採用（高確信度）
    ├─ LR_LOW：LRの予測を採用（低確信度）
    ├─ FALLBACK_KANJI：単一漢字辞書フォールバック
    ├─ FALLBACK_NUMERIC：漢数字ルールベース処理
    ├─ FALLBACK_ORPHAN：文字消失バグ救済
    └─ FALLBACK_々：々の繰り返し処理
    ↓
出力（読み + 信度 + 決定根拠）
```

#### 🌟 各フォールバックルールの詳細

##### 1. **BYPASS（ASCIIバイパス）**
- 特徴：ASCII印字文字（0x21-0x7E）で構成される連続ブロック
- 処理：LRを通さず、そのまま出力
- 理由：ASCII文字の読みはLRで学習する必要なし。データノイズ回避。

##### 2. **DICT（カスタム辞書）**
- 特徴：事前定義されたカスタム辞書にマッチした単語
- 処理：辞書の読みを強制適用（信度=1.0）
- 理由：固有表現や専門用語を確実に処理したい場合に使用

##### 3. **LR（LR予測・高確信度）**
- 特徴：LRの decision_function スコアを sigmoid で変換した信度が高い（デフォルト > 0.3）
- 処理：LRの予測ラベルをそのまま採用
- 理由：LRが十分な信度で判定できた

##### 4. **LR_LOW（LR予測・低確信度）**
- 特徴：LRの信度が低い（≤ 0.3）が、他のルールが適用されない
- 処理：LRの予測を採用するが、決定根拠に「LOW」タグを付与
- 理由：低精度だがフォールバック対象にもならない場合の苦肉の策

##### 5. **FALLBACK_KANJI（単一漢字辞書フォールバック）**
- 特徴：
  - 文字種が KANJI（漢字）
  - LRの信度が低い（< confidence_threshold）
  - 次の文字が「安全な送り仮名」（ひらがなで頻出のもの）
- 処理例：
  - 「走**る**」の「走」が低信度 → 単一漢字辞書から「ソウ」を取得
  - 「走」の次が「る」で、「る」は訓読み指標 → 訓読み「ハシ」を選択
- 理由：漢字単独では読みが複数種あるため、直後の送り仮名パターンから推測

##### 6. **FALLBACK_NUMERIC（漢数字ルールベース処理）**
- 特徴：文字種が JAPANESE_NUMERIC（漢数字）
- 処理：
  - 「一」「二」～「九」→ アラビア数字か音読みか、前後の文字から判定
  - 「十」「百」「千」「万」「億」「兆」→ 位取り文字の規則に従う
- マッピング例：「十」は前後の文字種により CONTINUE、「0」、「1」、「10」を出力
- 理由：数字系の読みは統計的変動が小さく、ルール化が効果的

##### 7. **FALLBACK_ORPHAN（文字消失バグ救済）**
- 特徴：読みラベルが「LABEL_CONTINUE」だが、「親」となる読みラベルがない
- 理由：LRが異常判定した場合、その文字の読みが消失する可能性を救済
- 処理：直前の有効な読みを引き継ぐか、デフォルト読みを適用

##### 8. **FALLBACK_々（々の繰り返し処理）**
- 特徴：文字が「々」（漢字の繰り返し記号）
- 処理：直前の文字の読みをそのまま繰り返す
- 例：「時々」→ 「時」=「トキ」 → 「々」=「トキ」

#### 決定根拠（DecisionSource）の記録

各文字の読みがどのルールで決定されたかを記録します：

```python
class DecisionSource:
    LR               = "LR"             # LRの予測（高確信度）
    LR_LOW           = "LR_LOW"         # LRの予測（低確信度）
    FALLBACK_KANJI   = "FALLBACK_KANJI" # 単一漢字辞書フォールバック
    FALLBACK_NUMERIC = "FALLBACK_NUM"   # 漢数字ルール処理
    FALLBACK_ORPHAN  = "FALLBACK_ORPH"  # 文字消失バグ救済
    FALLBACK_REPEAT  = "FALLBACK_々"    # 々繰り返し処理
    DICT             = "DICT"           # カスタム辞書マッチ
    BYPASS           = "BYPASS"         # ASCIIバイパス
```

この情報により、ユーザーは「なぜこの読みになったのか」を理解でき、必要に応じてカスタム辞書や設定で調整可能です。

### 3.3 複数モデルの統合と特徴設計

また、本実装では2つの独立したLRモデルを統合しています：

**モデル1：LinearSVC（多クラス分類、読みモデル）**
- クラス数：1000+（訓練データから生成）
- 出力：各特徴ベクトルに対する読みラベル
- decision_function による信度計算（sigmoid変換）

**モデル2：SGDClassifier（2値分類、境界モデル）**
- クラス数：2（「分かち書きなし」= 0、「分かち書きあり」= 1）
- 出力：各位置で分かち書きをするかどうか
- predict_proba で信度を直接取得可能

特徴量ベクトル化には独立した DictVectorizer を使用：

```python
# 読み用特徴ベクトル化
vect_read = DictVectorizer(sparse=True)
X_read = vect_read.fit_transform(X_dicts)

# 境界用特徴ベクトル化（通常、特徴は同じだが異なる重みが学習される）
vect_boundary = DictVectorizer(sparse=True)
X_boundary = vect_boundary.fit_transform(X_dicts)
```

### 3.4 後処理ルールによる精度向上

LRの局所的な特徴量（前後2文字の窓）によって、以下のような文脈パターンが統計的に学習されます：

```python
# 訓練データから抽出される特徴例
{
    'char': '金',           # 現在の文字
    'type': 'KANJI',        # 文字種
    'prev': '花',           # 前の文字
    'prev2': 'の',          # 2文字前
    'next': '星',           # 次の文字
    'next2': 'の',          # 2文字後
}
```

このような「局所文脈を埋め込んだ訓練データ」により、各ラベルの線形結合が自然な読みの分布に合致するよう重みが調整されます。それでも精度が足りない場合に、上記の8つのフォールバックルールが段階的に適用されます。

**効果：** データの質（文脈パターンの充実）を上げることで、LRでも文脈パターンの 85～95% が自然に学習可能；残りの問題はフォールバックルールで対処

## 4. 実現可能な機能

### 1. **超高速な自動かな変換**

テキスト→かな変換を行い、推論速度は Sudachi 等の従来法と同等メートルで実行可能。

### 2. **軽量な原文と読みの対応（リッチ・トークン）**

CRF ほどの複雑さなしに、リッチ・トークンの生成が可能。

### 3. **複数タスクの並列処理**

点訳では2つの独立したモデルを組み合わせて処理：

* **モデル1：読み推論（LinearSVC、多クラス分類）**
  - 各文字に対する読みラベルを確定
  - クラス数：1000+ （訓練データから自動生成）

* **モデル2：分かち書き判定（SGDClassifier、2値分類）
  - 各文字の直後で分かち書きを行うかどうかを判定
  - クラス数：2 （「なし」= 0、「あり」= 1）

これらを統合することで、単一の複雑なモデルより、メンテナンス性と精度が優れたシンプルな設計を実現。

### 4. **TTS / 点字用の読み分け**

内部的には LR で確率的に最も尤もらしい読みを選ぶが、代替案（2番目、3番目の候補）も保持可能。

### 5. **軽量モデルのオンタイム配布**

学習→モデル生成→バイナリ化→配布を、**数時間単位で回す** ことが可能になり、季節・文化的な用語変化への対応が柔軟。

## 5. 動作環境 (ターゲットスペック)

LR を採用することで、CRF では実現困難だった超軽量環境に対応できるようになります。

### 5.1 推奨環境（Linux組み込み）

| 項目 | ターゲットスペック | 備考 |
| --- | --- | --- |
| **対象OS** | Linux (Ubuntu, Debian, Alpine等) / 他のPOSIX環境 | CRF同等のOS依存性 |
| **CPU** | ARM Cortex-A シリーズ（500MHz以上推奨） | **CRFより低スペックで動作** |
| **RAM (メモリ)** | **8～16MB**（モデル展開時） | **CRF の30MB から1/5に削減** |
| **ストレージ** | **100～500KB** | 学習済みバイナリモデルのみ |
| **推論速度** | 1文あたり **5～20ミリ秒** | **CRF の1/10** |

### 5.2 必要最低環境（マイコン）

CRF では困難だった、本当のマイコン環境での実装が視野に：

| 項目 | 必要最低スペック | 備考 |
| --- | --- | --- |
| **対象** | ベアメタル / RTOS | OS不要 |
| **CPU** | 120MHz以上（ESP32, RP2040等） | **CRF では困難** |
| **内蔵SRAM** | **256KB以上** | Viterbi が不要なため大幅軽減 |
| **PSRAM / 外部RAM** | **512KB～2MB** | **CRF の1/4** |
| **ストレージ（Flash）** | **512KB以上** | モデルをFlashから直接参照可能 |
| **推論速度** | 1文あたり **10～30ミリ秒（想定）** | 体感リアルタイムで十分 |

※ CRF では実現不可能だった「1000円以下のマイコン上で動く日本語点字変換」が、LR で初めて実現可能になります。

## 6. アーキテクチャとデータ構造

CRF と同様に、リッチ・トークンの使用を継続しますが、より軽量な実装にします。さらに、**多段階のフォールバック戦略**を組み込んだ推論パイプラインが特徴です。

### 6.1 リッチ・トークンの定義（Python例）

```python
from dataclasses import dataclass

@dataclass
class RichToken:
    surface: str              # 元の表記（例: "4", "金星"）
    reading: str              # 読み（例: "よ", "きんぼし"）
    reading_confidence: float # LR の確信度スコア（0.0～1.0）
    is_split: bool            # 点字ルール上、直後で分かち書きをするか
    decision_source: str      # 決定根拠（BYPASS, DICT, LR, LR_LOW, FALLBACK_* など）
```

### 6.2 特徴量抽出のコードサンプル

```python
def extract_features_for_lr(sentence, i):
    """i番目の文字に対する特徴量を抽出する（LR向け）"""
    char = sentence[i]
    features = {
        'bias': 1.0,
        'char': char,
        'type': get_char_type(char),  # 文字種（KANJI/HIRAGANA/KATAKANA など）
    }
    
    # ウィンドウサイズ2：前後2文字のコンテキスト
    if i > 0:
        features['prev'] = sentence[i-1]
        if i > 1:
            features['prev2'] = sentence[i-2]
    if i < len(sentence) - 1:
        features['next'] = sentence[i+1]
        if i < len(sentence) - 2:
            features['next2'] = sentence[i+2]
    
    return features
```

この特徴ベクトルに対して、DictVectorizer で sparse 行列に変換し、LinearSVC/SGDClassifier に入力します。

## 8. まとめ：なぜ Logistic Regression か

| 観点 | CRF | LR + 多段階フォールバック |
|------|-----|-------------------------|
| **学習速度** | 2～5時間 | 30秒～5分 |
| **推論速度** | 50～200ms / 文 | 5～20ms / 文 |
| **メモリ効率** | 30MB～ | 5MB以下 |
| **実装の複雑さ** | 専門的な知識が必要 | 標準ライブラリ + ルールベース |
| **微調整の柔軟性** | 新データを追加するたびに大規模な再学習 | 新データへの迅速な対応が可能 |
| **組み込み対応** | マイコンは厳しい | Cortex-A 500MHz / RAM 8MB で動作可能 |
| **精度への対応** | 系列最適化で底上げ | フォールバックルールで個別対応 |

**結論：** 点訳というユースケースでは、CRFの「系列最適化」という強力さよりも、LRの「シンプルさ・高速性・軽量性」が圧倒的に実用的です。

本実装の**最大の工夫**は、LRの「独立判定」という限界を、以下の3層で補完する点です：

1. **訓練段階** ：前後2文字の局所文脈を特徴量に埋め込み、統計的に文脈パターンを学習
2. **推論前処理** ：ASCIIバイパス、カスタム辞書マッチングで「確実」な推論を先行実行
3. **推論後処理** ：8段階のフォールバックルール（KANJI辞書、漢数字ルール、文字消失救済等）で個別対応

これにより、**シンプルなLRでありながら、データの質と後処理ルール設計により、CRF相応の実用性を実現**しています。

さらに、結果には**決定根拠タグ（DecisionSource）** が付与されるため、ユーザーは「なぜこの読みになったのか」を理解できます。これは CI/CDサイクルや、点字使用者からの直接フィードバックに基づいた継続的改善を促進します。
