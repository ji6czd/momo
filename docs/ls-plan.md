# 線形モデルを用いた点字変換エンジンの再設計

## 1. CRF実装からの教訓と移行の背景

CRFを用いた実装を進める中で、以下の3つの重大な実装課題が明らかになりました。

### ① 学習時間の爆発的増加

CRFは系列全体の最適解を求めるため、訓練段階で複雑な計算（対数尤度の最大化、Viterbiアルゴリズムの繰り返し実行）が必要です。

- **実測値：** わずか1000行程度の訓練データで、学習に数時間以上を要する（CPUの小規模環境ではさらに深刻）
- **スケーラビリティの問題：** データが増えるほど計算量が増加し、実用的な訓練サイクルが困難

### ② 推論時間の遅延

- **予測の計算コスト：** 1文あたりの処理時間がSudachiなどの従来の辞書ベース手法より**大幅に長い**
- **スループットへの影響：** リアルタイムな点訳、特に点字ディスプレイへのストリーミング出力が遅延するリスク

### ③ メモリ消費の肥大化

CRFモデルは、全ての特徴の組み合わせに対する重みを保持します。

- **実測値：** 1000行程度のデータでも30MB以上のモデルサイズ（訓練過程でさらに多くのメモリを消費）
- **組み込みデバイスの制約：** 32MB以下のメモリを想定していた元の設計指針と乖離

### 結論：CRFは「強力だが重い」

CRFは強力な手法ですが、点訳という**軽量高速が求められるユースケース**では、オーバースペックであることが判明しました。

---

## 2. 解決策：線形分類器への転換

**LinearSVC（線形サポートベクターマシン）**は、CRFよりもはるかにシンプルな線形分類器です。

### 2.1 LinearSVC の基本概念

#### 特徴概要

- **単一の線形モデル：** 各特徴（文字、文字種、前後の文字）に対して線形の重みを学習するだけ
- **文字ごとの独立判定：** 系列全体の最適化ではなく、各位置で最も高スコアのラベルを局所的に選択（計算量が圧倒的に少ない）
- **ヒンジ損失による学習：** 正解ラベルのスコアが他のラベルより一定のマージン以上高くなるよう重みを調整

#### 数学的な定義（簡略版）

LinearSVC は以下の目的関数を最小化します：

$$
\min_{w, b} \frac{1}{2}\|w\|^2 + C \sum_i \max(0,\, 1 - y_i(w \cdot x_i + b))
$$

ここで：

- $w$ は各特徴に対する線形の重み（学習パラメータ）
- $b$ はバイアス項
- $C$ は正則化パラメータ（大きいほど訓練データへの適合を優先）
- 推論は単純な行列演算のみで、複雑な最適化アルゴリズムが不要

#### 多クラス分類への拡張（点訳での使用）

点訳では読みラベルが数百～数千個になるため、多クラス対応が必須です。scikit-learn では以下の戦略で対応します：

- **One-vs-Rest (OvR)** ：各クラス $c$ に対して、「クラス $c$ か否か」の2値分類器を訓練。
- **Decision Function** ：新しい入力に対して、全クラスのスコア $s_c$ を計算します：

$$
s_c(X) = w_c \cdot X + b_c
$$

例えば1500個のラベルがあれば、1500次元のスコアベクトルが得られます。

- **信度への変換（Sigmoid）** ：最大スコアのクラスを選んだ後、そのスコアを sigmoid で正規化して「信度（0～1）」に変換（Platt スケーリングの近似）：

$$
\text{confidence} = \frac{1}{1 + \exp(-s_{\text{selected}})}
$$

これにより、低い信度のラベルに対しては後述のフォールバックルールを適用できます。

### 2.2 LinearSVC の実用例

LinearSVC をはじめとする線形分類器は以下のような「分類タスク」で最も効果的です：

1. **テキスト分類（スパムメール検出、感情分析）**
   - シンプルな特徴量で高い精度
   - リアルタイムな推論が必要な場合に最適

2. **医療診断の補助**
   - 複数の測定値から疾患の確率を推定

3. **CTR予測（クリック率予測）**
   - 広告プラットフォームで、ユーザーの行動確率を初期判定

4. **推薦システムの基礎モデル**
   - 単純だが高速で、複数の候補をスコアリング

5. **系列ラベリングの簡易版**
   - 各位置の判定が独立に近い場合

6. **多クラス分類（scikit-learn の LinearSVC）**
   - 数百～数千のクラスを効率的に処理
   - 点字では「読みラベルの多様性」（1500程度の異なる読み）への対応に用いられる
   - decision_function でクラスごとのスコアを取得し、信度を計算

今のところラベルは1500程度です。大幅には増えないだろうと予想しています。

### 2.3 点訳への LinearSVC の応用メリット

#### ① 圧倒的な学習速度の高速化

CRFの場合：数時間～数十時間（データ量と特徴数に依存）
→ **LinearSVC：数分～数十分**

| 項目                   | CRF                              | LinearSVC                        |
| ---------------------- | -------------------------------- | -------------------------------- |
| **学習アルゴリズム**   | 勾配法 + Viterbi反復             | 座標降下法（liblinear）          |
| **学習時間（1000行）** | 1～5時間                         | 数分                             |
| **反復計算**           | 複雑な系列最適化                 | シンプルな重み更新               |
| **実用性**             | 重い前処理が必要                 | データ取得後すぐ実行可能         |

**メリット：** データのフィードバックループが爆速になり、「誤変換を記録 → 即座に再学習 → 修正版を配布」という反復改善が実現可能

#### ② 推論速度の大幅改善

- CRF: 複雑な動的計画法
  - 1文あたり 50～200ms

- LinearSVC: 線形変換のみ
  - 1文あたり 5～20ms（辞書ベースと同等か更に高速化可能）

**メリット：** オンラインでのリアルタイム推論が容易になり、点字ディスプレイへの遅延出力が実現可能

Pythonでの実装では50文字程度の文章で15ms程度でした。Rust実装では1ms程度で推論できています。

#### ③ メモリ効率の革命的改善

CRFとの同条件での比較はしていませんが、現在の実装では、モデルサイズは数十MB程度あります。Python実装では、実行時に数百MBになります。これはSudachi辞書などを使った方式よりおそらく多くのメモリーを必要としています。これは量子化するなどしてさらに削減する必要があります。

Rust実装ではモデルのバイナリが最大30MB程度で、実行時のメモリーも数十MB程度に収まっています。また、特徴量を削減したバージョンではモデルサイズが10MB程度にまで削減できています。

**メリット：** 32MB制約の組み込みデバイスで、実装的な余裕が生まれる

#### ④ 実装の単純化と版のパイプライン構築

LinearSVC は scikit-learn の標準実装であり：

```python
from sklearn.svm import LinearSVC

model = LinearSVC(C=1.0, max_iter=2000)
model.fit(X_train, y_train)          # 学習
scores = model.decision_function(X_test)  # 推論（スコアベクトル）
predictions = model.predict(X_test)       # 推論（ラベル）
```

点訳では、読み推論と分かち書き判定を**独立した2つのモデル**で実装：

```python
# 読み推論モデル（多クラス：LinearSVC）
model_read = LinearSVC(C=1.0, max_iter=2000)
model_read.fit(X_read, y_read)

# 分かち書き推論モデル（2値：SGDClassifier）
model_boundary = SGDClassifier(loss='modified_huber')
model_boundary.fit(X_boundary, y_boundary)
```

**メリット：** CRFの複雑な特徴設計、ハイパーパラメータチューニングが不要で、独立したモデルの組み合わせで柔軟性を確保

#### ⑤ モデル圧縮がさらに効率的

- **線形モデル** → 重みベクトルのみで記述可能（数KB～数百KB程度）
- **バイナリ化・固定小数点化** が容易
- **モデルの可視化・解釈** が簡単（どの特徴が重要かが一目瞭然）

## 3. LinearSVC の限界と克服方法 — 多段階フォールバック戦略

LinearSVC は圧倒的に高速・軽量ですが、CRFと異なり**各位置の判定が独立**であるという設計上の制約があります。この限界を補うため、本実装では**多段階のフォールバック戦略**を採用しています。

### 3.1 系列レベルの依存性が考慮されない

**制約：**

- CRF の場合：「前の文字が**何であるか**」が数学的に反映される
- LinearSVC の場合：「前の文字が**何か**」は特徴として入力するが、**モデル自体が系列の整合性を保証しない**

**例：**

- 「東京都」という3文字を LinearSVC で推論すると、各文字が独立に読みを確定します。
- CRF なら「この3文字の組み合わせで最も自然な読み系列」を探索しますが、LinearSVC はそこまでしません。

### 3.2 多段階フォールバック戦略

本実装では、LinearSVC の独立性の制約を、**複数層のフォールバックルール**で補完しています。推論パイプラインは以下のような決定フローを持ちます。

#### フォールバック戦略の全体構造

```
入力テキスト
    ↓
[前処理] source_seq 構築（拗音複合、位取り文字昇格）
    ↓
各文字を順に処理:
    ├─ bypass → ASCII・記号を原文のまま出力（信度 1.0、モデル不要）
    ├─ カタカナ（ヵ・ヶ除く）→ 原文のまま出力（信度 1.0、モデル不要）
    ├─ [スコア計算 + argmax]（単一文字辞書制約付き or 無制約）
    ├─ JAPANESE_NUMERIC + 低信度 → ルールベース変換 or Skip
    ├─ LABEL_CONTINUE 救済（3段階）
    │    ├─ 孤立 → 文字をそのまま出力
    │    ├─ Numeric → 数字素通し
    │    └─ 小書き仮名 → 親ラベル末尾に追記（拗音形成）
    ├─ LABEL_SKIP 救済
    │    └─ Numeric → 数字素通し
    └─ 通常ラベル出力
         ├─ 々フォールバック → モデルが不正なら直前漢字読みを繰り返す
         └─ ひらがな検証 → 不正予測なら直接カタカナ変換
    ↓
境界モデルによるスペース挿入（各文字後に判定）
    ↓
出力（読み + 信度 + 原文↔かな対応インデックス）
```

#### 各ルールの詳細

##### 1. **バイパス（ASCII・記号の素通し）**

- 対象：`is_bypass()` が真の文字（ASCII 印字文字、日本語句読点・記号類）
- 処理：モデルを通さず原文の文字をそのまま出力（信度 1.0）
- 理由：これらの文字の「読み」はモデルで学習する必要がなく、そのまま出力するのが正確

##### 2. **カタカナパススルー**

- 対象：文字種が `Katakana` で、助数詞用小書きカタカナ（ヵ U+30F5、ヶ U+30F6）を除くもの
- 処理：モデルを通さず原文のまま出力（信度 1.0）。拗音（キャ等の複合ユニット）もまとめて出力
- 理由：カタカナはそれ自体が読みそのものであり、モデル予測が不要

##### 3. **単一文字辞書制約付き argmax**

- 対象：文字種が `Kanji` または `Numeric`（算用数字）で、単一文字辞書（`single_character_dic.tsv`）が設定されている場合
- 処理：モデルのスコアを計算したあと、argmax を「辞書に存在する読み」の中だけで行う
- 目的：辞書外の誤った読みが選ばれるのを防ぐ。信度に関わらず常時適用
- 算用数字での例：`1` の候補を辞書の `{"1", "ヒト", "ツイ"}` に絞ることで、他の数字の読み（`3` の「ミッ」等）が誤って選ばれるのを防ぐ

##### 4. **JAPANESE_NUMERIC フォールバック（漢数字ルールベース変換）**

- 条件：文字種が `JapaneseNumeric`（漢数字・位取り文字）かつモデルの信度が閾値未満
- 変換ルール：
  - 漢数字（〇一二…九、壱弐参）→ ASCII 数字 ("0"–"9")
  - 十：前後の文字種に応じて "10" / "1" / "0" / Skip
  - 百：同様に "100" / "1" / "00" / "0"
  - 千：単独 "セン"、「三千」は連濁で "ゼン"、右に数字なら "0"
  - 万 → "マン"、億 → "オク"、兆 → "チョー"
- 理由：数字系の読みはルール化が容易で、モデルが苦手な低頻度パターンをカバー

##### 5. **LABEL_CONTINUE 救済（3段階）**

モデルが `---`（LABEL_CONTINUE）を予測したとき、「この文字は直前ラベルに包含される」という意味になる。以下の3段階で処理する：

1. **孤立救済**：親が存在しない・bypassが親・漢字以外が親の場合  
   → 文字をそのまま出力（`emit_char_passthrough`）。この文字を新たな親とする
2. **Numeric + CONTINUE 救済**：文字種が `Numeric`（アラビア数字）の場合  
   → 数字をそのまま素通しで出力
3. **小書き仮名 + CONTINUE 救済**：文字が小書き仮名（ぁぃぅ…ッャュョ等）でかつ親がまだ小書き仮名を持っていない場合  
   → 親ラベルの末尾に挿入することで拗音（キャ、シュ等）を正しく形成  
   （ひらがな小書きは +0x60 でカタカナ化してから挿入）

それ以外の CONTINUE → 単純スキップ（親情報は更新しない）

##### 6. **LABEL_SKIP 救済**

モデルが `_`（LABEL_SKIP）を予測したとき：

- **Numeric + SKIP 救済**：文字種が `Numeric` の場合 → 数字をそのまま素通しで出力
- それ以外 → 単純スキップ

##### 7. **々フォールバック（繰り返し記号の処理）**

- 条件：文字が「々」（U+3005）かつ直前に漢字の読みが記憶されている（`last_fallback`）かつモデルの予測が不正（`is_valid_repeat` が偽）
- 処理：`last_fallback`（直前漢字の読み）をそのまま採用
- 連濁対応：「神々（かみがみ）」のように先頭音節が連濁する場合も、ライマンの法則に反しない限り有効な予測として許容（フォールバック不要）
- 例：「国々」→「国」="コク" → 「々」="コク"

##### 8. **ひらがな検証**

- 処理：ひらがな文字に対してモデルの予測を検証（`is_valid_kana_prediction`）し、不正なら直接カタカナ変換
- 合法的な例外として以下を許容：
  - 「は」→「ワ」（格助詞としての読み）
  - 「へ」→「エ」（格助詞としての読み）
  - 「う」→「ー」（長音）
- それ以外の予測が想定外の場合 → 原文ひらがなをカタカナに直接変換して出力

### 3.3 複数モデルの統合と特徴設計

また、本実装では2つの独立した線形モデルを統合しています：

#### モデル1：LinearSVC（多クラス分類、読みモデル）

- クラス数：1500程度（訓練データから生成）
- 出力：各特徴ベクトルに対する読みラベル
- decision_function による信度計算（sigmoid 変換による近似）
- メモリ制約時は `--sgd` オプションで SGDClassifier(loss='hinge') に切り替え可能

#### モデル2：SGDClassifier（2値分類、境界モデル）

- クラス数：2（「分かち書きなし」= 0、「分かち書きあり」= 1）
- 出力：各位置で分かち書きをするかどうか
- predict_proba で信度を直接取得可能（loss='modified_huber'）

特徴量ベクトル化には独立した DictVectorizer を使用：

```python
# 読み用特徴ベクトル化
vect_read = DictVectorizer(sparse=True)
X_read = vect_read.fit_transform(X_dicts)

# 境界用特徴ベクトル化（通常、特徴は同じだが異なる重みが学習される）
vect_boundary = DictVectorizer(sparse=True)
X_boundary = vect_boundary.fit_transform(X_dicts)
```

### 3.4 後処理ルールによる精度向上

LinearSVC の局所的な特徴量（前後3文字のウィンドウ、ウィンドウサイズ7）によって、以下のような文脈パターンが統計的に学習されます：

```python
# 訓練データから抽出される特徴例（window=7 の場合）
{
    'char': '金',           # 現在の文字
    'type': 'KANJI',        # 文字種
    'prev': '花',           # 前の文字
    'prev2': 'の',          # 2文字前
    'prev3': '山',          # 3文字前
    'next': '星',           # 次の文字
    'next2': 'の',          # 2文字後
    'next3': '空',          # 3文字後
}
```

このような「局所文脈を埋め込んだ訓練データ」により、各ラベルの線形結合が自然な読みの分布に合致するよう重みが調整されます。それでも精度が足りない場合に、上記の8つのフォールバックルールが段階的に適用されます。

**効果：** データの質（文脈パターンの充実）を上げることで、LinearSVC でも文脈パターンの 85～95% が自然に学習可能；残りの問題はフォールバックルールで対処

## 4. 実現可能な機能

### 1. **超高速な自動かな変換**

テキスト→かな変換を行い、推論速度は Sudachi 等の従来法と同等レベルで実行可能。

### 2. **軽量な原文と読みの対応（リッチ・トークン）**

CRF ほどの複雑さなしに、リッチ・トークンの生成が可能。

### 3. **複数タスクの並列処理**

点訳では2つの独立したモデルを組み合わせて処理：

- **モデル1：読み推論（LinearSVC、多クラス分類）**
  - 各文字に対する読みラベルを確定
  - クラス数：1500程度（訓練データから自動生成）

- **モデル2：分かち書き判定（SGDClassifier、2値分類）**
  - 各文字の直後で分かち書きを行うかどうかを判定
  - クラス数：2（「なし」= 0、「あり」= 1）

これらを統合することで、単一の複雑なモデルより、メンテナンス性と精度が優れたシンプルな設計を実現。

### 4. **TTS / 点字用の読み分け**

内部的には LinearSVC で最も高スコアの読みを選ぶが、代替案（2番目、3番目の候補）も保持可能。

### 5. **軽量モデルのオンタイム配布**

学習→モデル生成→バイナリ化→配布を、**数時間単位で回す** ことが可能になり、季節・文化的な用語変化への対応が柔軟。

## 5. 動作環境 (ターゲットスペック)

LinearSVC を採用することで、CRF では実現困難だった超軽量環境に対応できるようになります。

### 5.1 推奨環境（PC）

| 項目             | ターゲットスペック              | 備考                       |
| ---------------- | ------------------------------- | -------------------------- |
| **対象OS**       | Windows 10/11, macOS, Linux     | クロスプラットフォーム対応 |
| **CPU**          | x86-64 シリーズ（1GHz以上推奨） | **CRFより大幅に軽量化**    |
| **RAM (メモリ)** | **16～64MB**（モデル展開時）    | Python実装では数百MBが必要 |
| **ストレージ**   | **15MB～50MB**                  | 学習済みバイナリモデルのみ |

Python実装では、モデルサイズは数十MB程度で、実行時には数百MB程度のメモリを消費しています。Rust実装ではモデルサイズが10～30MB程度で、実行時のメモリも数十MB程度に収まっています。

### 5.2 推奨環境（Linux組み込み）

| 項目             | ターゲットスペック                               | 備考                                                 |
| ---------------- | ------------------------------------------------ | ---------------------------------------------------- |
| **対象OS**       | Linux (Ubuntu, Debian, Alpine等) / 他のPOSIX環境 | CRF同等のOS依存性                                    |
| **CPU**          | ARM Cortex-A シリーズ（1GHz以上推奨）            | Raspberry Pi Zeroでは厳しい印象です                  |
| **RAM (メモリ)** | **10～30MB**（モデル展開時）                     | 最も小さなモデルなら32MBのボードで動くかもしれません |
| **ストレージ**   | **15～50MB**                                     | 学習済みバイナリモデルのみ                           |
| **推論速度**     | 1文あたり **10～20ミリ秒**                       | **CRF の1/100**                                      |

※ CRF では実現不可能だったLinuxワンボードコンピュータ（Raspberry Pi Zeroなど）での動作が可能になります。

│ 入力: 元の日本語テキスト                                   │
└─────────────────────┬─────────────────────────────────┘
                      │
          ┌───────────▼────────────────────────────┐
          │ ステップ1: 前処理 (to_source_seq)        │
          │ - 拗音複合ユニット検出                   │
          │ - 位取り文字の JapaneseNumeric 昇格      │
          └───────────┬────────────────────────────┘
                      │
          ┌───────────▼───────────────────────────────┐
          │ ステップ2: 特徴抽出 (compute_source_features) │

          └───────────┬───────────────────────────────┘
                      │
          ┌───────────▼──────────────────────────────────┐
          │ ステップ3: 文字ごとに推論＋フォールバック適用  │

## 9. まとめ：なぜ LinearSVC か

| 観点               | CRF                                    | LinearSVC + 多段階フォールバック    |
| ------------------ | -------------------------------------- | ----------------------------------- |
| **学習速度**       | 2～5時間                               | 30秒～5分                           |
| **推論速度**       | 50～200ms / 文                         | 1～20ms / 文                        |
| **実装の複雑さ**   | 専門的な知識が必要                     | 標準ライブラリ + ルールベース       |
| **微調整の柔軟性** | 新データを追加するたびに大規模な再学習 | 新データへの迅速な対応が可能        |
| **組み込み対応**   | マイコンは厳しい                       | Cortex-A 1GHz / RAM 32MB で動作可能 |
| **精度への対応**   | 系列最適化で底上げ                     | フォールバックルールで個別対応      |

**結論：** 点訳というユースケースでは、CRFの「系列最適化」という強力さよりも、LinearSVCの「シンプルさ・高速性・軽量性」が圧倒的に実用的です。

本実装の**最大の工夫**は、LinearSVCの「独立判定」という限界を、以下の3層で補完する点です：

1. **訓練段階** ：前後3文字の局所文脈（ウィンドウサイズ7）を特徴量に埋め込み、統計的に文脈パターンを学習
2. **推論前処理** ：バイパス（ASCII・記号）とカタカナパススルーで「確実」な文字を先行処理
3. **推論後処理** ：単一文字辞書制約付き argmax・漢数字ルールベース・LABEL_CONTINUE/SKIP 救済・々フォールバック・ひらがな検証 の多段階ルールで個別対応

これにより、**シンプルな線形分類器でありながら、データの質と後処理ルール設計により、CRF相応の実用性を実現**しています。
