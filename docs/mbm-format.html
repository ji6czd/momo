Inside the .mbm file

A single binary blob holds everything the Rust engine needs to turn Japanese text into Braille — no Python, no external tables. Here is what those bytes are, in the exact order the loader reads them.

§1 統合語彙テーブル Unified vocabulary × n_features

Maps each feature key to everything the models need for it: the reading/linear feature_id and, for GBDT, the categorical (column, code). One binary search serves all three consumers. feature_id is implicit — the row order is the id, so it isn't stored.

§3 読みモデル重み Reading weights · CSC × n_nonzero · the bulk

The sparse weight matrix (n_classes × n_features), int8-quantized with a per-class scale. Stored column-major (CSC) so the loaded array is already the shape inference walks.

The bias term added to each class's score before argmax — kept as full f32, it is tiny.

§5 境界モデル Boundary model algo_tag · self-describing

Decides spacing between segments. A one-byte tag says which of two algorithms follows. Since v0x07 the GBDT variant carries only its trees — its categorical mappings live in §1 — so this section is now ~1 MB.

§6 人名辞書テーブル Person-name dictionary × n_names

Surface forms of names, each with optional per-unit readings — feeds the B/I name-flag features and a fixed-reading fallback. Empty (0) for dictionary-less models.

Where the bytes actually go

Measured on a real model (window=5, 22.5 MB at v0x07), two sections carry almost everything:

統合語彙 §159%
読み重み §3 CSC36%
境界 §5 trees · 辞書5%
ラベル · intercept<1%

v0x07 unified the vocabulary. Through v0x06 the GBDT boundary shipped its own cat_vocab — a categorical re-encoding of essentially the same ~n_features keys already in §1 — so the file stored the vocabulary twice (the two copies were ~60% of the file). v0x07 folds the categorical (column, code) into each §1 entry and drops the explicit feature_id (now the row index), leaving one vocabulary. The boundary section keeps only its ~1 MB of trees. Measured effect: file and load-time peak both fell ~1/3 (window=5: 32.9→22.5 MB), with zero change to any predicted result.

Inside the reading weights (§3), the sparse layout costs, per non-zero, a value plus the index of where it sits. Storing that index as u16 not u32, and going column-major (CSC) so no transpose happens at load, trims both the file and the load-time peak.

The .mbmf sidecar shares this layout byte-for-byte, except §3 and the linear §5 keep raw f32 weights (no quant_scale). Same version number; only the magic — MBMF vs MOMO — tells them apart.
