> 一般リリース後、別ブランチで扱う項目。

## 背景 ― なぜこの方向か

点字の社会的な位置づけが動いている:

- 紙の点字読者は減少中。公共配慮の主役は Web や音声コードへ移りつつある。
  → 点訳プログラムは「本を作る道具」から少しずつ外れる。
- 一方でスクリーンリーダー＋**点字ディスプレイ**の利用は残る。紙を読まない人でも
  点字ディスプレイは使う。最近の点字ディスプレイは Android 搭載機も出てきている。

つまり momo の主戦場は **「バッチで組版（desktop/server、RAM 潤沢）」から
「逐次・常駐・端末内で訳す（常にメモリに居座る）」へ移る**。後者で momo が
共存/置換する相手は **liblouis**（テーブルは KB〜数MB）。この文脈では常駐 20〜45MB は
「大きめ」ではなく **部品として成立するかの分かれ目**になる。メモリ倹約は装飾ではなく
生き残りの条件。

### mmap が効く核心

二分探索は N 個のうち `log2(N)≈18` 個しか触らない。原理的に全部を常駐させる必要はない。
その現代版が **mmap（デマンドページング）** ── 手書きのバンク切り替え（EMS 的なこと）は不要で、
OS/MMU が触ったページだけ引き込む。

Android/組み込みでの本当の利点は「小ささ」以上に **行儀の良さ**:
mmap したモデルは**クリーンなファイルバックのメモリ**なので、逼迫時に OS がタダで破棄でき、
必要時にファイルから再フォルトできる。40MB の匿名ヒープは dirty で OOM Killer の標的だが、
mmap なら常時起動のアクセシビリティサービスでも殺されにくい。**上限の張られた常駐**になる。

## ターゲット行列（mmap の効き）

| ターゲット | mmap | 備考 |
|---|---|---|
| Android 点字ディスプレイ / スマホ | ✅ | Linux。クリーン・再フォルト可能で OOM に強い（主目的） |
| デスクトップ SR（NVDA=Windows） | ✅ | メモリマップドファイル可 |
| MCU | ✅ (XIP) | flash を execute/read-in-place できれば SRAM に写さず探索。SRAM 常駐 ~数十KB |
| Web (WASM) | ❌ | linear memory はフラット。ネットワーク越しのデマンドページング不可。<br>ただし Web は最もメモリを許せる（タブ40MB は許容、転送は brotli 3〜5MB） |

**「載せない設計が効かない場所（Web）が、ちょうど載せても困らない場所」** という並び。

## 現状の障害（v0x07 時点）

1. **ロード時の再ソート**: Python の dict 順 ≠ Rust の Ord 順のため、`loader.rs` は
   語彙を全部 `Vec` に読み込んでから `sort_by(|a,b| a.key.cmp(&b.key))` する。
   この再ソートがある限り全 materialize が必須。
2. **可変長 FeatureKey**: キーごとに長さが違うと、マップしたバイト列を添字で
   直接二分探索できない。
3. **v0x07 の feature_id 暗黙化との衝突**: 暗黙 id は「行順 = feature_id 順」を要求。
   ゼロコピー bsearch は「キー順」を要求。**同じ表を2通りに並べられない。**

## PC 上の一次計測（2026-08-16、GO/NO-GO 判断材料）

本実装（exporter のキー順ソート化・no_std 化等）に着手する前に、「作ってみないと
測れない」を避けるため、現行 v0x07 のデータをそのまま固定幅バイナリへ複製し、
mmap 経由で読んだ場合の速度・メモリ影響だけを PC 上で切り出して計測した。
使い捨てテスト（本番コードには不使用）: [`momors-core/src/mmap_experiment.rs`](../momors/crates/momors-core/src/mmap_experiment.rs)
（`#[cfg(test)]` + `#[ignore]`、`cargo test -- --ignored --exact <test名>` で個別実行）。

### 速度: 語彙 bsearch も境界 GBDT も mmap で悪化しない

- **語彙 bsearch**（w=4: 語彙31.8万件、w=7: 107.6万件・ウォーム定常状態）:
  mmap/Vec 比 **0.93〜1.02倍**（誤差レベル）。ページキャッシュに乗った後は
  mmap 経由でも Vec 常駐とコストが変わらないという理屈通りの結果。
- **境界 GBDT 木**（`TreeNode` は boundary.rs 内 private のため実木は読めず、
  設計メモの規模感「木300本・約1MB」に合わせた合成木で代替検証）:

  | 実装 | 1文字(300本合計)あたり | 対Boxポインタ木比 |
  |---|---|---|
  | 今と同じ `Box<TreeNode>` ポインタ木 | 28,333 ns | (基準) |
  | フラット配列（Vec 常駐） | 20,167 ns | **0.71倍**（29%速い） |
  | フラット配列（mmap） | 21,024 ns | **0.74倍**（26%速い） |

  flat→mmap の追加コストは+4%のみ。効いているのは **mmap の有無ではなく
  Box ポインタ木からフラット配列への変換そのもの**（300本×約127ノードが
  ヒープ上に散らばっていたのがキャッシュミスの主因）。
- **戦略的な帰結**: 「データをフラット配列にする」のは mmap するか否かに
  関係なく無条件の勝ち。一度フラット（固定幅バイナリ）にしてしまえば、
  **「Vec に全展開 vs mmap」は解釈コードが同一のただのロード戦略の差**になる
  （ファイル全読み込みで得た `Vec<u8>` をバイト列としてキャストしても、
  `Mmap` から得た `&[u8]` をキャストしても同じ関数で読める）。→ 下記
  「トレードオフ」の「2レイアウト共存」懸念は、**1レイアウト＋ターゲット別
  ロード戦略**で足りる可能性が高い。

### メモリ: 「常に小さい」ではなく「フルロードよりやや軽く、回収可能」

実コーパス（`dataset/basic_raw.tsv`）を流し、Windows の Working Set で
Vec 全展開版と mmap 版を比較（vocab + CSC のみ。読みラベル/人名辞書/
境界重みは対象外・小さいので大勢に影響しない見込み）。

| モデル | 実文量 | 触れた語彙の割合 | Vec常駐 | mmap常駐 | 削減率 |
|---|---|---|---|---|---|
| w=4 | 100文 | 7.4% | 22.3MB | 19.3MB | 約13% |
| w=4 | 2000文 | 49.2% | 22.7MB | 19.6MB | 約14% |
| w=7 | 2000文 | 46.3% | 52.5MB | 49.8MB | 約5% |

想定より削減幅が小さい。原因は「二分探索は毎回 log2(N) 箇所しか触らない」が
**クエリ単位の話**であること: 実文章は特徴量タイプが多様なので、異なる
キーへの bsearch は配列内の異なる領域を探索する。統合語彙は全タイプを
1本の配列にソートしているため、たった7.4%しか語彙エントリに「ヒット」
していなくても、探索経路（≒ページ）は配列のほぼ全域に散らばり、ほぼ
全体をフォールトインしてしまう。→ 本文書が既に懸念していた
「working set の誤解を避ける」を実測でむしろ強く裏付けた。**mmap の
価値は「縮小」ではなく「クリーン＝OS圧迫時に回収可能」であることに
一段と絞られる。** 縮小そのものを狙うなら、特徴量タイプごとに領域を
分けたサブテーブル（タイプ→範囲のトップレベル索引）で探索を局所化する
案が有望（未検証）。

### 1文字あたりの完全なコストと ESP32-P4 への含意

読みモデル（語彙bsearch+CSC）だけでなく境界GBDTも含めた実測: **w=4モデル・
実コーパスで約42,000〜44,000 ns/文字**（PC・ウォーム状態）。内訳は読み候補
32.5件/字（ヒット15.1件/字）に対し、**総コストの8割強が境界GBDT
（木300本を毎文字フル評価）**。語彙 bsearch は主要因ではなかった。

[`esp32-mcu-feasibility.md`](esp32-mcu-feasibility.md) への含意:

- クロック比（PC数GHz vs P4 RISC-V 400MHz ≈ 9倍）に、分岐の多い木走査が
  組み込みコアの弱点である分（OoO/大キャッシュ不在で追加3〜10倍悪化しがち）
  を掛けると、ラフな外挿で **1〜4ms/文字** 程度になりそうだが、これは
  推定であり実測ではない。同文書が最初のマイルストーンとして挙げている
  「P4実機でw=4をflashに焼いてmmapし、1文字の推論時間を実測する」で
  決着させるべき数字。
- 上記レンジは同文書が既に見積もっていた「PSRAM/flashミス込みで
  1〜5ms/文字でも読速度は楽に超える」の範囲に収まる。
- **境界GBDTが総コストの8割強を占める**ため、MCU向けの最優先の高速化
  レバーは mmap 化そのものではなく、同文書が既に候補として挙げている
  「MCUティア向けに木の本数/深さを削った軽い境界モデル」である可能性が高い。

## mmap 対応レイアウトが要求すること

- exporter が**最初からキー順（Rust Ord）で並べて書く**（ロード時ソート撤廃）。
- 可変長 FeatureKey を畳む: **固定幅化**（無駄はあるが添字 bsearch が自明）
  vs **オフセット表**（コンパクトだが間接参照が一段増える）。
  → `FeatureKey` は実装上すでに固定長 POD（`feature_type` + `u8val` + `ct[3]` + `cp[3]`、
  `Copy`）なので、語彙側は固定幅化がほぼ無償（詳細は下記「PC上の一次計測」）。
  GBDT木の `cats: Vec<u32>` のような本当に可変長のデータだけオフセット表
  （共有プールへの offset/len）にする、のハイブリッドで良さそう（合成木検証で確認済み）。
- **feature_id を明示フィールドに戻す**（暗黙化を一部差し戻し、+4B/エントリ）。
  キー順格納と両立させるため。resident 制約ターゲットでは十分に割の良い交換。
- ゼロコピー読み出しのための**アラインメント**。
- loader は **固定幅バイナリを解釈するだけ**にし、`Vec` へ意味的な変換をしない
  （ソート不要・型変換不要）。その上で、その固定幅バイト列を **mmap するか
  ファイル全読み込みの `Vec<u8>` にするかはターゲットごとのロード戦略として選べる**
  （解釈コードは同一。詳細は下記「PC上の一次計測」）。

## トレードオフ / 割り切り

- **+4B/エントリ**（明示 id）と、固定幅化した場合の空間の無駄。だが常駐激減の対価としては小さい。
- **Web は恩恵ゼロ**（WASM フラットメモリ）。→ ただし PC上の一次計測で「固定幅バイナリに
  なっていれば mmap も Vec 全展開も同じ解釈コードで読める」ことを確認できたため、
  **2レイアウトを維持する必要はなく、1レイアウト＋ロード戦略の切り替え**で足りる
  可能性が高い（Web/バッチは `Vec<u8>` へ全読み込み、常駐/組み込みは mmap）。
  当初懸念していた `.mbm` / `.mbmf` サイドカーのような二重メンテナンスは避けられそう。
- **working set の誤解を避ける**: 長い文書を連続で読むと累積では語彙のかなりを
  フォルトインしうる。「WS は常に小さい」とは言い切れない。本当の効き目は
  **クリーン＝回収可能**であること（逼迫時に落ちて再フォルトされる）。単なる縮小ではない。

## 主線 / 副線の分岐（意識として持っておく）

- **主線（未来）**: 逐次・常駐・端末内翻訳 → mmap/XIP 前提の materialize しないフォーマット。
- **副線 / レガシー**: バッチ組版（全部載せる、w=5/7、desktop/server）。

**v0x07 の最適化（feature_id 暗黙化・ストリームで Vec に読み込む）は副線を磨いたもの。**
悪い投資ではない（ファイルも RAM も実測 1/3 減）。ただし主線が「載せない」なら、
次の一手は最適化の延長ではなく別設計になる ── feature_id 暗黙化は一部差し戻す。

## 未確定・保留

- MCU は momo（ML）の土俵か、liblouis 的ルールの領域か。小さい MCU は後者かもしれない
  （日本語が本質的に不可逆で ML 前提、という momo の立ち位置とのすり合わせ）。
- ~~固定幅 vs オフセット表の選択（実測して決める）~~ → 一次計測で概ね決着:
  語彙（`FeatureKey`）は固定幅、GBDT木の `cats` のような真の可変長データだけ
  オフセット表、のハイブリッドで良い（詳細は「PC上の一次計測」）。
- 語彙をさらに小さくする「Web/SR ティア」モデル（学習側の低頻度特徴量刈り込み）は
  フォーマットとは別軸。mmap と併用しうる。
- **新規**: 境界GBDTの軽量化（MCUティア向けに木の本数/深さを削る）は、一次計測では
  mmap化そのものより速度への影響が大きいレバーに見える。優先順位を要検討。
- **新規**: 特徴量タイプ別のサブテーブル化（bsearchの探索領域を局所化し、常駐削減幅を
  伸ばせる可能性）は未検証。
