## 背景 ― なぜこの方向か

点字の社会的な位置づけが動いている:

- 紙の点字読者は減少中。公共配慮の主役は Web や音声コードへ移りつつある。
  → 点訳プログラムは「本を作る道具」から少しずつ外れる。
- 一方でスクリーンリーダー＋**点字ディスプレイ**の利用は残る。紙を読まない人でも
  点字ディスプレイは使う。最近の点字ディスプレイは Android 搭載機も出てきている。

つまり momo の主戦場は **「バッチで組版（desktop/server、RAM 潤沢）」から
「逐次・常駐・端末内で訳す（常にメモリに居座る）」へ移る**。後者で momo が
共存/置換する相手は **liblouis**（テーブルは KB〜数MB）。この文脈では常駐 20〜45MB は
「大きめ」ではなく **部品として成立するかの分かれ目**になる。メモリ倹約は装飾ではなく
生き残りの条件。

### mmap が効く核心

二分探索は N 個のうち `log2(N)≈18` 個しか触らない。原理的に全部を常駐させる必要はない。
その現代版が **mmap（デマンドページング）** ── 手書きのバンク切り替え（EMS 的なこと）は不要で、
OS/MMU が触ったページだけ引き込む。

Android/組み込みでの本当の利点は「小ささ」以上に **行儀の良さ**:
mmap したモデルは**クリーンなファイルバックのメモリ**なので、逼迫時に OS がタダで破棄でき、
必要時にファイルから再フォルトできる。40MB の匿名ヒープは dirty で OOM Killer の標的だが、
mmap なら常時起動のアクセシビリティサービスでも殺されにくい。**上限の張られた常駐**になる。

## ターゲット行列（mmap の効き）

| ターゲット | mmap | 備考 |
|---|---|---|
| Android 点字ディスプレイ / スマホ | ✅ | Linux。クリーン・再フォルト可能で OOM に強い（主目的） |
| デスクトップ SR（NVDA=Windows） | ✅ | メモリマップドファイル可 |
| MCU | ✅ (XIP) | flash を execute/read-in-place できれば SRAM に写さず探索。SRAM 常駐 ~数十KB |
| Web (WASM) | ❌ | linear memory はフラット。ネットワーク越しのデマンドページング不可。<br>ただし Web は最もメモリを許せる（タブ40MB は許容、転送は brotli 3〜5MB） |

**「載せない設計が効かない場所（Web）が、ちょうど載せても困らない場所」** という並び。

## 現状の障害（v0x07 時点）

1. **ロード時の再ソート**: Python の dict 順 ≠ Rust の Ord 順のため、`loader.rs` は
   語彙を全部 `Vec` に読み込んでから `sort_by(|a,b| a.key.cmp(&b.key))` する。
   この再ソートがある限り全 materialize が必須。
2. **可変長 FeatureKey**: キーごとに長さが違うと、マップしたバイト列を添字で
   直接二分探索できない。
3. **v0x07 の feature_id 暗黙化との衝突**: 暗黙 id は「行順 = feature_id 順」を要求。
   ゼロコピー bsearch は「キー順」を要求。**同じ表を2通りに並べられない。**

## PC 上の一次計測（2026-08-16、GO/NO-GO 判断材料）

本実装（exporter のキー順ソート化・no_std 化等）に着手する前に、「作ってみないと
測れない」を避けるため、現行 v0x07 のデータをそのまま固定幅バイナリへ複製し、
mmap 経由で読んだ場合の速度・メモリ影響だけを PC 上で切り出して計測した。
使い捨てテスト（本番コードには不使用）: [`momors-core/src/mmap_experiment.rs`](../momors/crates/momors-core/src/mmap_experiment.rs)
（`#[cfg(test)]` + `#[ignore]`、`cargo test -- --ignored --exact <test名>` で個別実行）。

### 速度: 語彙 bsearch は mmap で悪化しない（境界GBDT木は下記の訂正を参照）

- **語彙 bsearch**（w=4: 語彙31.8万件、w=7: 107.6万件・ウォーム定常状態）:
  mmap/Vec 比 **0.93〜1.02倍**（誤差レベル）。ページキャッシュに乗った後は
  mmap 経由でも Vec 常駐とコストが変わらないという理屈通りの結果。
  → この結論は実装・実モデルでも再確認済み（v0x08実装時、語彙のキー順
  ソート化のみで速度が完全に不変であることを確認）。**この項目は結論変わらず有効。**
- **境界 GBDT 木**（当時は `TreeNode` が boundary.rs 内 private で実木を読めず、
  設計メモの規模感「木300本・約1MB」を想定した**合成木**で代替検証していた）:

  | 実装 | 1文字(300本合計)あたり | 対Boxポインタ木比 |
  |---|---|---|
  | 今と同じ `Box<TreeNode>` ポインタ木 | 28,333 ns | (基準) |
  | フラット配列（Vec 常駐） | 20,167 ns | **0.71倍**（29%速い） |
  | フラット配列（mmap） | 21,024 ns | **0.74倍**（26%速い） |

  > ⚠️ **この合成木ベンチマークの結論は誤りだった**。後日実際にフラット化を実装し
  > 実モデルで検証したところ、逆に**40〜60%遅化**した（下の「境界GBDT木の
  > フラット化 ― 実装後に撤回した記録」参照）。合成木は1splitあたりカテゴリ
  > 1〜8個を仮定していたが、実モデルは平均約28個/split（catsプール全体で約1MB）
  > あり、この前提のズレが結論を逆転させた。**この表は「合成ベンチマークだけで
  > GO/NO-GO判断をしてはいけない」という教訓として残す**（削除せず反面教師として
  > 保持）。

- **戦略的な帰結（語彙については有効、木については撤回）**: 語彙のように
  元々1本のソート済み配列であるデータは、フラット（固定幅バイナリ）にすれば
  **「Vec に全展開 vs mmap」は解釈コードが同一のただのロード戦略の差**になる
  （ファイル全読み込みで得た `Vec<u8>` をバイト列としてキャストしても、
  `Mmap` から得た `&[u8]` をキャストしても同じ関数で読める）。これは実装・実測で
  裏付けが取れている。→ ただし「データをフラット配列にするのは無条件の勝ち」
  という一般化は誤りだった。GBDT木のように**小さいノードが大量にあり、かつ
  可変長の付随データ（cats）を持つ構造**では、フラット化＝共有プール化が逆に
  キャッシュ局所性を壊すことがある。「フラット化の効果はデータの形状次第」
  というのが今回の一番の教訓。

### メモリ: 「常に小さい」ではなく「フルロードよりやや軽く、回収可能」

実コーパス（`dataset/basic_raw.tsv`）を流し、Windows の Working Set で
Vec 全展開版と mmap 版を比較（vocab + CSC のみ。読みラベル/人名辞書/
境界重みは対象外・小さいので大勢に影響しない見込み）。

| モデル | 実文量 | 触れた語彙の割合 | Vec常駐 | mmap常駐 | 削減率 |
|---|---|---|---|---|---|
| w=4 | 100文 | 7.4% | 22.3MB | 19.3MB | 約13% |
| w=4 | 2000文 | 49.2% | 22.7MB | 19.6MB | 約14% |
| w=7 | 2000文 | 46.3% | 52.5MB | 49.8MB | 約5% |

想定より削減幅が小さい。原因は「二分探索は毎回 log2(N) 箇所しか触らない」が
**クエリ単位の話**であること: 実文章は特徴量タイプが多様なので、異なる
キーへの bsearch は配列内の異なる領域を探索する。統合語彙は全タイプを
1本の配列にソートしているため、たった7.4%しか語彙エントリに「ヒット」
していなくても、探索経路（≒ページ）は配列のほぼ全域に散らばり、ほぼ
全体をフォールトインしてしまう。→ 本文書が既に懸念していた
「working set の誤解を避ける」を実測でむしろ強く裏付けた。**mmap の
価値は「縮小」ではなく「クリーン＝OS圧迫時に回収可能」であることに
一段と絞られる。** 縮小そのものを狙うなら、特徴量タイプごとに領域を
分けたサブテーブル（タイプ→範囲のトップレベル索引）で探索を局所化する
案が有望（未検証）。

### 1文字あたりの完全なコストと ESP32-P4 への含意

読みモデル（語彙bsearch+CSC）だけでなく境界GBDTも含めた実測: **w=4モデル・
実コーパスで約42,000〜44,000 ns/文字**（PC・ウォーム状態）。内訳は読み候補
32.5件/字（ヒット15.1件/字）に対し、**総コストの8割強が境界GBDT
（木300本を毎文字フル評価）**。語彙 bsearch は主要因ではなかった。

[`esp32-mcu-feasibility.md`](esp32-mcu-feasibility.md) への含意:

- クロック比（PC数GHz vs P4 RISC-V 400MHz ≈ 9倍）に、分岐の多い木走査が
  組み込みコアの弱点である分（OoO/大キャッシュ不在で追加3〜10倍悪化しがち）
  を掛けると、ラフな外挿で **1〜4ms/文字** 程度になりそうだが、これは
  推定であり実測ではない。同文書が最初のマイルストーンとして挙げている
  「P4実機でw=4をflashに焼いてmmapし、1文字の推論時間を実測する」で
  決着させるべき数字。
- 上記レンジは同文書が既に見積もっていた「PSRAM/flashミス込みで
  1〜5ms/文字でも読速度は楽に超える」の範囲に収まる。
- **境界GBDTが総コストの8割強を占める**ため、MCU向けの最優先の高速化
  レバーは mmap 化そのものではなく、同文書が既に候補として挙げている
  「MCUティア向けに木の本数/深さを削った軽い境界モデル」である可能性が高い。

## 境界GBDT木のフラット化 ― 実装後に撤回した記録（2026-08-16）

上の合成木ベンチマークを受けて、実際に `.mbm`/`.mbmf` v0x08 として実装した
（語彙のキー順ソート化と同時に、`Box<TreeNode>` 再帰木 → インデックスベースの
フラット配列 + 共有 `cats_pool` へ変更）。正しさは実モデルで確認できた
（新旧の実装で予測結果が完全一致）。しかし **実モデル（w=4/5/7、いずれも
GBDT境界）で1文字あたりの推論速度を計測したところ、一貫して40〜60%遅化した**:

| モデル | 旧（Boxポインタ木） | 新（フラット配列+共有catsプール） | 悪化率 |
|---|---|---|---|
| w=4 | 43,666 ns/字 | 69,841 ns/字 | 1.60倍 |
| w=5 | 46,497 ns/字 | 70,387 ns/字 | 1.51倍 |
| w=7 | 52,688 ns/字 | 73,404 ns/字 | 1.39倍 |

**原因**: 実モデルの境界GBDTは1splitあたり平均**約28個**のカテゴリコードを
持つ（`cats_pool` 全体で約25万エントリ・約1MB）。合成ベンチマークは1〜8個を
仮定していたため、この差が結論を逆転させた。1文字の推論で境界木を約3,500
ノード分辿っており（300本×平均約12段。GBDTは葉優先成長のため木が不均等に
深くなりうる）、そのたびに1MBの共有 `cats_pool` の散発的な位置へアクセスする
アクセスパターンが、旧来の「splitノードごとに小さい専用 `Vec<u32>` を持つ」
方式よりキャッシュに悪かった、というのが最有力の説明（語彙のmmap一次計測で
見た「1本の大きい配列への散発アクセスは局所性を壊す」のと同じ系統の現象）。

**判断**: 境界GBDT木のフラット化は**撤回**し、v0x07までと同じ
`Box<TreeNode>` 再帰構造・再帰ノード列に戻した。v0x08 は**語彙のキー順
ソート化+feature_id明示化のみ**を含む（`momors-core/src/boundary.rs` は
無変更）。予測結果・速度ともv0x07から不変であることを確認済み。

境界木のフラット化を再挑戦するなら、catsを大きい共有プールに追い出すのではなく、
ノードローカルな固定長インライン配列や木単位のローカルプールなど、
アクセス局所性を壊さない設計を先に実測してから、が教訓。

## ESP32-P4 実機での借用ロード判定（2026-09-05）― 見送り

本文書が「着手の契機」に挙げていた具体ハード（ESP32-P4）が動くようになったので、
loader を書き換える前に **「フラッシュ読みは PSRAM の何倍遅いか」だけ**を実機で測った。
測定コマンドと詳細な数字は [`esp32p4-plan.md` §7 の 2026-09-05 の記録](esp32p4-plan.md)。

| `:xip`（4MB・同一乱数系列） | フラッシュ DIO@80MHz | フラッシュ QIO@80MHz |
|---|---|---|
| bsearch プローブ (flash/psram) | 23.3x | **5.46x** |
| CSC 列 96B 連続読み (flash/psram) | 7.1x | **2.13x** |

**判定: 借用ロードは見送り**（このボードでは）。理由は 2 つ:

1. **払う先が悪い**。境界GBDTの反転索引化（commit 6d0eb31）で境界の比重が下がり、
   1文字コストの重心は **読みモデル側（語彙引き + CSC 読み）** に移った
   （実機 `:probe`: lookup 73µs / read 181µs / boundary 147µs）。借用ロードは
   まさにそこをフラッシュに落とす。外挿で **437 → 850µs/字（約2倍）**。
   本文書が 2026-08 に書いた「境界GBDTが8割だから語彙bsearchのmmap化は安い」という
   前提は、境界の高速化によって**消滅した**。
2. **買うものが要らない**。PSRAM 32MB 中 17.25MB が空いている。

ただし DIO 時代の「10倍遅くなる」から「2倍」に落ちたので、**選択肢としては生きている**。
効くのは「PSRAM が無い/小さいボード」「w5 を載せたい」とき。

### 再挑戦時のための知見

- **借用するなら語彙から。CSC は最後**。合成ベンチの比だけ見ると CSC(2.13x) のほうが
  安全に見えるが、**MBあたりでは逆**: 語彙は 10.2MB 消せて 1文字あたり数十ライン、
  CSC は 4.2MB しか消せないのに 1文字あたり nnz 11,433×3B ≈ 34KB（128Bライン換算 268本）を
  舐める。常駐14.4MBの内訳は **語彙 10.2MB（318,971件×32B）/ CSC 4.2MB**。
- **フラッシュのバス幅とキャッシュライン長が支配項**。QIO 化だけで比が 4 倍改善した。
  借用ロードの損得は「アルゴリズム」ではなく **1ラインの充填コスト** で決まる
  （128Bライン: DIO@80 で 6.4µs、QIO@80 で 3.2µs、PSRAM 200MHz で約1µs）。
  XIP を本気でやるなら **ラインを 64B に縮める**方が、レコード16〜32Bのランダム
  アクセスには合う（PSRAM 側の局所性とトレードオフ）。
- **合成ベンチは絶対値の外挿に使わない**（[境界GBDT木のフラット化の教訓](#境界gbdt木のフラット化--実装後に撤回した記録2026-08-16)の再確認）。
  実アクセスは同じ特徴量キーが文字をまたいで繰り返すため、`:probe` 実測は
  130ns/プローブで `:xip` の PSRAM 443ns/プローブより 3.4 倍速い。比としては
  両側に同じだけ効くので妥当だが、絶対値は別物。
- **固定幅化するとファイルが膨らむ**。`.mbm` 全体が 11.8MB なのに対し、語彙を 32B
  固定幅で並べると語彙だけで 10.2MB。model パーティション 12MB では収まらなくなる。

## mmap 対応レイアウトが要求すること（語彙のみ。境界木は上記の通り対象外）

- exporter が**最初からキー順（Rust Ord）で並べて書く**（ロード時ソート撤廃）。
  → **実装済み・v0x08として着手済み**（語彙テーブルのみ）。
- 可変長 FeatureKey を畳む: **固定幅化**（無駄はあるが添字 bsearch が自明）
  vs **オフセット表**（コンパクトだが間接参照が一段増える）。
  → `FeatureKey` は実装上すでに固定長 POD（`feature_type` + `u8val` + `ct[3]` + `cp[3]`、
  `Copy`）なので、語彙側は固定幅化がほぼ無償（詳細は上記「PC上の一次計測」）。
  GBDT木の `cats: Vec<u32>` のような可変長データを共有プールへオフセット表化
  する案は、**実測の結果撤回**（上記「境界GBDT木のフラット化」参照）。
- **feature_id を明示フィールドに戻す**（暗黙化を一部差し戻し、+4B/エントリ）。
  キー順格納と両立させるため。resident 制約ターゲットでは十分に割の良い交換。
- ゼロコピー読み出しのための**アラインメント**。
- loader は **固定幅バイナリを解釈するだけ**にし、`Vec` へ意味的な変換をしない
  （ソート不要・型変換不要）。その上で、その固定幅バイト列を **mmap するか
  ファイル全読み込みの `Vec<u8>` にするかはターゲットごとのロード戦略として選べる**
  （解釈コードは同一。詳細は下記「PC上の一次計測」）。

## トレードオフ / 割り切り

- **+4B/エントリ**（明示 id）と、固定幅化した場合の空間の無駄。だが常駐激減の対価としては小さい。
- **Web は恩恵ゼロ**（WASM フラットメモリ）。→ ただし PC上の一次計測で「固定幅バイナリに
  なっていれば mmap も Vec 全展開も同じ解釈コードで読める」ことを確認できたため、
  **2レイアウトを維持する必要はなく、1レイアウト＋ロード戦略の切り替え**で足りる
  可能性が高い（Web/バッチは `Vec<u8>` へ全読み込み、常駐/組み込みは mmap）。
  当初懸念していた `.mbm` / `.mbmf` サイドカーのような二重メンテナンスは避けられそう。
- **working set の誤解を避ける**: 長い文書を連続で読むと累積では語彙のかなりを
  フォルトインしうる。「WS は常に小さい」とは言い切れない。本当の効き目は
  **クリーン＝回収可能**であること（逼迫時に落ちて再フォルトされる）。単なる縮小ではない。

## 主線 / 副線の分岐（意識として持っておく）

- **主線（未来）**: 逐次・常駐・端末内翻訳 → mmap/XIP 前提の materialize しないフォーマット。
- **副線 / レガシー**: バッチ組版（全部載せる、w=5/7、desktop/server）。

**v0x07 の最適化（feature_id 暗黙化・ストリームで Vec に読み込む）は副線を磨いたもの。**
悪い投資ではない（ファイルも RAM も実測 1/3 減）。ただし主線が「載せない」なら、
次の一手は最適化の延長ではなく別設計になる ── feature_id 暗黙化は一部差し戻す。

## 未確定・保留

- MCU は momo（ML）の土俵か、liblouis 的ルールの領域か。小さい MCU は後者かもしれない
  （日本語が本質的に不可逆で ML 前提、という momo の立ち位置とのすり合わせ）。
- ~~固定幅 vs オフセット表の選択（実測して決める）~~ → 決着（ただし当初の想定とは逆）:
  語彙（`FeatureKey`）は固定幅化で問題なし（実装・実測済み）。GBDT木の `cats` を
  共有プールへオフセット表化する案は**実装・実測の結果撤回**（「境界GBDT木の
  フラット化」参照）。「可変長データは何でもオフセット表にすればいい」わけではなく、
  アクセスパターン・データ形状次第という教訓が残った。
- 語彙をさらに小さくする「Web/SR ティア」モデル（学習側の低頻度特徴量刈り込み）は
  フォーマットとは別軸。mmap と併用しうる。
- 境界GBDTの軽量化（MCUティア向けに木の本数/深さを削る）は、境界GBDTが1文字コストの
  8割強を占める以上、mmap化やフラット化より速度への影響が大きいレバーのまま
  （フラット化が撤回された今、これが唯一の残る有力な高速化案）。優先順位を要検討。
- 特徴量タイプ別のサブテーブル化 → **2026-09-10 に実装・実測（version 0x09）**。
  下の節を参照。常駐削減の狙いを超えて、ファイルサイズと速度にも効いた。
- 境界GBDT木のフラット化の再挑戦（ノードローカルなインライン配列・木単位の
  ローカルプールなど、cats共有プール以外の設計）は未検証。優先度は低い
  （境界木の軽量化の方が筋が良さそうなため）。

## 特徴量タイプ別サブテーブル化の実装記録（2026-09-10・version 0x09）

上の「未検証」だった案を実装した。**当初の狙い（常駐削減）を超えて、
ファイルサイズと速度にも効いた**ので、経緯と数字を残す。

### 着手の判断が変わった経緯

最初は「メモリ内の構造だけ変えてファイル形式は据え置き」と判断した。理由は
「形式を変えても w5 は ESP32-P4 のフラッシュに載らないから」。**これは誤りだった**。
閾値（w5 が載るか）で評価したせいで、連続量（データ増に何倍まで耐えられるか）を
見落としていた。実測すると:

| | 実測 |
|---|---|
| モデルパーティション（`momors-esp32/partitions.csv`） | 0xC00000 = 12.00 MiB |
| w4 の `.mbm`（v0x08） | 11.33 MiB |
| **成長余地** | **1.06 倍**（余白 5.9%） |

学習データは今後 2 倍まで増える予定があり、**w4 は既に限界だった**。

### 実データで確かめた前提

3 モデル（w4/w5/w7）を直接パースして確認した。

| 前提 | 結果 |
|---|---|
| コードポイントは 21bit に収まるか | `>= 2^21` は 0 件（実測最大 U+20B9F） |
| `cat_column` は `feature_type` の純関数か | 複数列を持つタイプは 0 件 |
| 詰めた u64 の昇順がファイル順と一致するか | 完全一致（ロード時の再ソートが不要） |
| `feature_id` は 0..N-1 の順列か | YES（採番し直せる） |
| 列コードは列単位で 0..n-1 の全単射か | YES（採番し直せる） |
| CSC の列あたり最大 nnz | 1,595（= n_classes、u16 に収まる） |

`cat_column` が型の関数であるのは構造的な性質。`momo_py/categorical.py` の
`fit_categorical()` が「特徴量名ごとに 1 列」を作り、特徴量名が `FeatureType` と
1 対 1 に対応するため。**唯一の例外**は `char_s` 列で、`CharSelf`(0x90) と
`CharSelfCompound2`(0xA6) の 2 タイプが共有する（Python 側でどちらも `char_s=...`
という名前を出す）。このためコードは「タイプ内で 0..n-1」ではなく「**列内で**
0..n-1」の全単射になり、セクションごとの `cat_code_base` で吸収した。

### 何を変えたか

エントリが持っていた 3 つのフィールドを全部採番し直して暗黙にし、
1 エントリ = 詰めた u64 キー 8B だけにした。

- `feature_id` = セクション先頭 ID + 添字。exporter がキー順に採番し直し、
  **CSC の列と線形境界の重みを同じ順に並べ替える**。
- `cat_code` = `cat_code_base` + 添字。exporter が列ごとにキー順で採番し直し、
  **GBDT の `cats` を書き換える**。
- `cat_column` = セクションが 1 個持つ。

CSC の `colptr`（u32 累積和）も `col_len`（u16）に変えた。

### 結果

| model | ファイル v0x08 | v0x09 | 削減 | 12.0MiB に対する成長余地 |
|---|---|---|---|---|
| w4 | 11.33 MiB | 6.23 MiB | -45.0% | 1.06倍 → **1.93倍** |
| w5 | 23.84 MiB | 12.50 MiB | -47.6% | 0.50倍 → 0.96倍 |
| w7 | 36.38 MiB | 18.15 MiB | -50.1% | 0.33倍 → 0.66倍 |

| model | 語彙の常駐 | 変更前 | タイプ別分割のみ | +暗黙化 | 合計 |
|---|---|---|---|---|---|
| w4 | | 9.76 MiB | 4.88 | 2.44 | **-75%** |
| w5 | | 20.64 MiB | 10.32 | 5.16 | **-75%** |
| w7 | | 33.01 MiB | 16.51 | 8.25 | **-75%** |

速度（PC・release・実コーパス 351,728 文字）:

| model | wall µs/char 前 | 後 | 改善 | 語彙引き 前 → 後 | ロード |
|---|---|---|---|---|---|
| w4 | 7.45 | 5.79 | -22.3% | 1.83 → 0.60 (-67%) | 8 ms |
| w5 | 14.54 | 11.86 | -18.4% | 3.11 → 1.07 (-66%) | 15 ms |
| w7 | 18.81 | 14.33 | -23.8% | 4.69 → 1.73 (-63%) | 20 ms |

**速度が想定を上回った理由**: 20B 構造体の辞書順比較（型→u8val→ct×3→cp×3 の
分岐連鎖）が u64 1 個の比較になった定数倍が、キャッシュ常駐率の改善に上乗せされた。
着手前は「語彙引きは全体の 13%（P4 実測）だから天井は 1 割強」と見ていたが、
PC では語彙引きが 21〜25% を占めており、そこが 3 分の 1 になった。

### ローダーの簡略化（副次的な狙い）

- `read_feature_key()` を**削除できた**（呼び出し元が `read_vocab` だけだった）。
  1 エントリごとの 10 前後の分岐と 5〜8 回の細かい read が、セクションヘッダ +
  キー配列の一括読みになった。
- `float_loader.rs` の `sort_by` 全ソートを削除（`loader.rs` は検証だけという
  非対称も解消）。
- 語彙の全体ソート順検証が、セクション内の狭義単調増加チェックになった。
- **障害 2「可変長 `FeatureKey`」と障害 3「行順 vs キー順の両立不能」が両方消えた。**
  セクション内は固定幅で、キー順に採番し直したので両方の順序が一致する。
  mmap 化のときローダーは「セクションを切り出してスライスを持つ」だけになる。

### 検証

- 実コーパス 351,728 文字のかな・分かち・点字が **6 スナップショットすべてバイト一致**
- momors-core 257 テスト・momo-py の exporter テスト通過
- 点訳回帰テストの不一致は既知の 4 件のみ（新規なし）

### 残っている案

- 静的 B 木（S+ tree）レイアウト。8B キー × 16 個 = 128B ライン 1 本なので分岐数 17・
  深さ 5（最大セクション 150,013 件）。触るラインが 17 本から 5 本に落ちる見込み。
  Eytzinger より有利と見ているが、P4 はインオーダでプリフェッチ命令も期待できないため
  **実機で比較してから決める**。
- 境界 GBDT の `build_membership` から `partition_point` を消す
  （`cat_code` をロード時に「`col.splits` 内の (start, len)」へ置き換える）。
  期待値は小さいので、`Phase::Boundary` の内訳を分けてから判断する。

## 差分 + varint レイアウトの実装記録（2026-09-13・version 0x0A）

v0x09 のあと、ファイルの内訳は「ソート済みの配列」がほぼすべてになった
（語彙の u64 キー・CSC の `rowind`/`col_len`・GBDT の `cats`）。ソート済み配列は
隣との差分が小さいので、**差分を LEB128 varint で書く**だけで汎用圧縮なしに
半分になる。zlib -9 で丸ごと圧縮した場合（57〜59% 減）の 8 割方まで届く。

ユーザーの評価（2026-09-13）は「これはゼロコピーをするより、現実的な成長戦略
かもしれません」。フラッシュが律速の P4 に対して、RAM を増やさずファイルだけを
縮める手なので、借用ロード（上記 2026-09-05 で見送り）と直交する。

### 何を変えたか

- ヘッダ flags **bit1 = `FLAG_DELTA_VARINT`**。立っているとき、以下をソートされた
  単位ごとに「先頭の値 + 隣との差分」の varint 列で書く:

  | 配列 | 区切り |
  |---|---|
  | 語彙キー (u64) | セクションごと |
  | CSC `col_len` (u16) | 差分なし。値ごとに varint（大半が 1 バイト） |
  | CSC `rowind` (u16) | 列ごと（`col_len` で区切る。列内はクラスID昇順） |
  | GBDT `split_feature` / `n_cats` | 差分なし。値ごとに varint |
  | GBDT `cats` (u32) | split ごと |

  CSC の `data` (i8)・ヘッダ・ラベル・quant_scale・intercept・木の
  `node_tag`/`default_left`/`leaf_value`・辞書は固定幅のまま。
- ローダーは `ArrayLayout { Fixed, DeltaVarint }` を flags から決めて
  `read_vocab` / `read_csc_structure` / `parse_tree_node` に渡す。**展開後の
  メモリ構造は v0x09 と同一**（`Vec<u64>` / `colptr` / `rowind` / `Box<TreeNode>`）。
  推論経路には触れていない。
- exporter の**既定は圧縮形**。`--fixed-width` で固定幅（flags bit1 = 0）も書ける。
  差分符号化した配列は mmap でそのまま二分探索できないので、ゼロコピーの道を
  塞がないために残した。`.mbmf` も同じ 2 モード（構造を共有しているため）。
- フィクスチャは `fixture_delta.mbm` / `fixture_gbdt_delta.mbm` を追加し、固定幅版と
  展開結果が一致することをテストする。

### 結果

| model | v0x09 | v0x0A | 12.0MiB への成長余地 |
|---|---|---|---|
| w4 | 6.30 MiB | **3.36 MiB (-47%)** | 1.90倍 → **3.57倍** |
| w5 | 12.66 MiB | **6.72 MiB (-47%)** | 0.95倍 → **1.79倍** |
| w7 | 18.39 MiB | **9.46 MiB (-49%)** | 0.65倍 → **1.27倍（w7 も載る）** |

セクション別（w4、v0x09 → v0x0A）: 語彙 2.47 → 0.60 MiB、読み重み 3.47 → 2.58 MiB
（うち `data` 0.95 MiB は据え置き）、境界木 0.26 → 0.11 MiB。

- 実コーパス 351,728 文字のかな・分かち・点字が **6 スナップショットすべてバイト一致**
  （固定幅で書いた v0x0A ファイルでも一致）
- momors-core 262 テスト・momo-py の exporter テスト 20 件通過
- PC (w7) のプロセス起動〜1 行処理: 70ms → 95ms。varint 復号のぶん増えるが、
  フラッシュから読む量が半分になる P4 では相殺されうる。**P4 実機はモデルを
  焼き直して `:stat` / `:bench` で測ること（未計測）**。
- RAM は設計どおり不変（Duo の w5 OOM には効かない）。

### 残っている案

- CSC `data` (i8) のエントロピー符号化。残る最大項だが、値の分布はソートと無関係で
  差分の手は効かない。汎用圧縮ではなく量子化ビット幅の見直しと一体で考える。
- 語彙の静的 B 木レイアウトは、圧縮形と両立しない（固定幅モード専用の案になる）。
