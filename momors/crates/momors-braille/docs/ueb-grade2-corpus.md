# UEB Grade 2 仕様書 — Phase 9「規範の用例コーパスで測る」

Phase 8 まで、規範の用例は**読んだところだけ**テストにしていた。Phase 9 では
**Appendix 2「Word List」を丸ごと回帰コーパスにする**。1,029語すべてに期待する点字と
適用規則番号が付いているので、実装の穴が数字で見える。

抽出には注意が要る。PDF は語も点字も**行で折り返す**ので、素朴に1行ずつ読むと期待値が
途中で切れる（`US (United States)` の点字は2行、`IT (Information Technology)` は原文が2行）。
継続行を繋ぐ状態機械にして初めて正しく取れた。

- コーパス: `dataset/ueb_appendix2_words.tsv`（原文 / 期待する点字 / 規則番号）
- テスト: `tests/ueb_appendix2.rs`（`KNOWN_FAIL` に未対応語を明示）
- 出典: The Rules of UEB 2024 (ICEB), Appendix 2。ICEB が Creative Commons で公開。

## 1. なぜ liblouis ではなく原典なのか

`liblouis/tables/en-ueb-g2.ctb` にも同種の語リスト（`sufword` / `begword` が534件）があり、
実際に突き合わせると**418語で我々が過剰縮約**していた。使えるデータではある。しかし採らなかった:

- **ライセンス**: liblouis のテーブルは LGPL-2.1+、momo は BSD-3-Clause。語リストを取り込むと
  そのデータは LGPL の派生物になる。単語自体は事実でも、「どの語を選んで並べたか」は彼らの成果。
- **規範性**: liblouis は実装であって規範ではない。原典なら実装のバグを引き継がない。
- **規則番号**: 原典の Word List は各語に**適用される規則番号**が付く。不一致が出たとき、
  どの規則を実装できていないかが即座に分かる。これが決定的だった。

liblouis は**取り込まずに突き合わせ相手として使う**ぶんには問題ない。

### データで直ったもの（採掘）

不一致語に対して「どこに区切りを入れれば規範の点字になるか」を総当たりで探し、
`[divisions]` に 155件、`initial_stems` に 26件を機械的に追加した。

- `cart|horse` `bottle|neck` `two|fold` `tea|room` … 複合語の境界
- `anemo|ne` `colo|nel` `canto|nese` … **音節の境界**（`one` の頭字符は1音節のときだけ。§10.7.6）
- `begonia` `behemoth` `congee` `disaster` … be/con/dis が第一音節の語

音節境界が出てきたので、セクション名を `[morphemes]` から **`[divisions]`（語の区切り）** に改めた。
UEB が「語の構成や音節の切れ目を跨ぐ縮約は使わない」と定めている以上、区切りは形態素だけではない。

### 機構が要ったもの（データでは表せない）

- **§10.4.2**: `ch/sh/th/wh/ou/st` の groupsign が**語全体**に一致すると、その語ではなく wordsign の
  語として読まれてしまう（`sh` は `⠩`＝「shall」に見える）。そういうときは文字で書く（`sh` = `⠎⠓`）。
- **§10.5.1/2/3**: 下方 wordsign の接触制限が3者バラバラだった。`be/were/his/was` は
  下方約物（**ハイフン・ダッシュを含む**）に接すると使えない（`would-be` = `⠺⠙⠤⠃⠑`）。
  `enough` には制限がない（`had-enough` = `⠸⠓⠤⠢`）。`in` は**その並びに上方の点があれば**使える
  （`in-depth` = `⠔⠤⠙⠑⠏⠹`、しかし `in.` は `⠊⠝⠲`）。データ（`avoid_lower_punct` /
  `needs_upper_dot`）で3者を区別した。
- **§10.7.4**: `ever` は `e` / `i` の直後では使わない（`believer` = `⠆⠇⠊⠑⠧⠻`）。`not_after = "ei"`。
- **§10.1.2/§10.2.2**: アポストロフィの後ろが `'s 't 'd 'll 're 've` のときだけ、その語は
  「並び全体で1語」になる。`it's` の `it` は wordsign を使えるが、`t'do` `more'n` `you'm` は使えない。
- **§10.9.9 の誤読検出（一般化）**: Phase 8 は §10.9.3 の10語だけを見ていたが、**読み戻し**で
  判定するのが正しかった。セル列を shortform として読み戻した語がリストにあれば誤読される
  （`UNSD` の `sd` → `unsaid` はリストにある → `⠰⠰`。`wisdom` の `sd` → `wisaidom` は無い → 不要）。
  我々自身が `unsaid` を `⠥⠝⠎⠙` と書く以上、`UNSD` は本当に曖昧だった。

### 採掘は「その語が直る」だけでは足りない

再採掘で6語の候補が出たが、**2件は却下**した。コーパス全体では退行が出なかったのに、
普通の語を壊すからである（コーパスは安全網として不完全）。

- `wh|ere`（`where'er` を直す）→ **普通の `where` を壊す**（`⠐⠱` が `⠱⠻⠑` になる）
- `a|boutface`（`ABOUTface!` を直す）→ **リストの語 `aboutface` を壊す**

どちらも本当の原因は区切りではない（typeform と大文字の規則）。**区切りで表せないものを
区切りで表すと、別の語が壊れる**。採用したのは `disin|genuous`（真の区切り）と、
語そのものに閉じる `bei|n` `he|rf` `h|ereford` の4件。

## 3. 残る16語（`KNOWN_FAIL`）

| 理由 | 語 |
|---|---|
| typeform 符が未対応 | Quickbraille, SuperBraille, GreatGrandChild |
| §10.9.6（技術用語・略語では縮約しない。語リストが要る） | mst file, Somesch River |
| §10.1.3 頭字語では wordsign を使わない（**発音の知識**に依る。規範も "preferably"。`CAN Network` は縮約する） | US (United States), IT (Information Technology) |
| 語ごとの発音・語構成に依る例 | ABOUTface!, Al, BEd, Ch'ing, cofounder, Conn., hoity-toity, mod cons, where'er |

最後の群は「データを足せば直る」ものだが、1語ずつ規範を確かめる必要があるので保留にした。
`KNOWN_FAIL` を減らすのが今後の作業になる。**増えたら退行**としてテストが落ちる。

## 4. この作業のやり方について

規範の用例をそのまま回帰テストに落とすやり方は、Phase 6 以降ずっと効いている。今回も
`bear`（strong > lower）や `in-depth`（下方 wordsign の接触制限）のような、**仕様書を読んだだけでは
気づけない**誤りをコーパスが暴いた。仕様を足すときは、まず出典の用例をテストにすること。
